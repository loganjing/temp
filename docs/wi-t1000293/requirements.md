# 工单系统需求（业务任务 121-full）

## 1. 目标

为多公司用户提供工单管理系统：提交人创建并跟踪工单；公司按分类将工单自动分配到业务组；业务组成员处理工单、多轮回复并在必要时转派；工单完成后由提交人进行满意度评价。（来源：用户明确提出）

## 2. 角色与核心对象

### 角色
- **提交人（用户）**：创建工单、参与回复、在工单完成后进行满意度评价。提交人具有姓名、邮箱、公司、部门等基本信息。（用户明确提出，其中部门信息在"处理时查看提交人完整信息"中明确）
- **处理人**：业务组成员，处理分配到本组的工单、回复、执行转派。（用户明确提出）
- **公司业务组/成员/分配规则的管理操作执行者**：用户未指定具体角色。（未规定；推荐基线：由具有该公司管理权限的用户执行，权限模型本身未规定）

### 核心对象
- **工单**：工单ID、主题、描述、分类、SLA优先级（P0-P4）、提交人信息（含邮箱）、创建时间、当前状态、回复记录、处理记录、转派记录、满意度评价。（用户明确提出）
- **公司**：提交人所属，可拥有多个业务组。（用户明确提出）
- **业务组**：公司下可创建多个，每个业务组可设置成员。（用户明确提出）
- **分配规则**：公司级"分类 → 业务组"映射，用于工单自动分配。（用户明确提出）
- **分类（问题分类）**：工单的问题分类；具体分类取值未规定，由使用方在使用中维护。（未规定；推荐基线：系统支持维护分类列表，供创建工单时选择）

## 3. 核心行为与规则

### 3.1 工单创建与信息（用户明确提出）
- 提交人可创建工单，填写：主题、描述、分类、SLA优先级（P0-P4）。
- 系统自动生成工单ID，并记录提交人信息（含邮箱）与创建时间。
- 创建成功后，可通过工单详情读回上述全部字段。
- SLA优先级的设置者未规定（推荐基线：提交人创建工单时选择 P0-P4）。

### 3.2 多轮回复（用户明确提出）
- 同一工单支持多轮回复；每条回复记录回复人、回复时间及回复内容。
- 可回复的角色未规定（推荐基线：提交人与工单当前处理方均可回复）。
- 回复列表可读回并按回复时间排序展示。

### 3.3 工单生命周期（状态集合：用户明确提出；流转触发：推荐基线）
状态集合：**创建、待分配、待处理、完成、取消**。
- 提交成功后，工单初始状态为"创建"。
- 进入分配流程后为"待分配"；命中公司分类分配规则或完成人工分配、确定业务组后为"待处理"。
- 处理人完成处理后为"完成"。
- "取消"为分支终态：可执行取消操作的前置状态与操作者未规定（推荐基线：非终态下提交人或当前处理方可取消；取消后工单不再进入处理流程）。

### 3.4 工单分配（用户明确提出）
- 公司可增加多个业务组，每个业务组可设置成员；配置结果可读回。
- 公司可配置"分类 → 业务组"的自动分配规则；该公司的新工单按分类自动分配到对应业务组，工单状态进入"待处理"。
- 分类未命中任何规则时工单的去向未规定（推荐基线：停留"待分配"，等待人工分配）。

### 3.5 工单转派（用户明确提出）
- 处于处理中的工单可执行转派操作，变更当前处理方（业务组成员/业务组）。
- 转派后工单保持"待处理"，可继续被处理与回复。
- 转派记录：推荐基线——记录转派人、转派对象与转派时间，可在工单上追溯；用户未明确字段要求，本基线以"转派后处理方可观察变更"为最小要求。

### 3.6 工单处理（用户明确提出）
- 处理人处理工单时，可查看提交人的完整信息：姓名、公司、部门、历史工单（该提交人提交过的工单）等。
- 处理完成后，系统记录处理人、处理时间、工单状态（完成）。

### 3.7 用户评价（用户明确提出）
- 工单完成后，提交人可对该工单进行满意度评价。
- 评价结果可读回。评价的具体形式与量表未规定（推荐基线：满意度评分）。

## 4. 用户旅程（端到端）

**提交人旅程**：提交人创建工单（主题、描述、分类、优先级）→ 系统生成工单ID并记录提交人信息与创建时间 → 工单进入分配流程 → 提交人可与处理方多轮回复沟通 → 工单完成 → 提交人进行满意度评价。

**处理方旅程**：公司配置业务组、成员与分类分配规则 → 该公司新工单按分类自动分配到对应业务组，状态为待处理 → 处理人查看提交人完整信息（姓名、公司、部门、历史工单）→ 回复沟通，必要时转派 → 完成处理，系统记录处理人、处理时间与状态 → 等待提交人评价。

## 5. 验收场景

### AC-01：提交人可创建工单并读回完整基础信息
- 验收条件：提交人创建的工单包含工单ID、主题、描述、分类、SLA优先级（P0-P4）、提交人信息（含邮箱）和创建时间；创建成功后可通过工单详情读回全部字段。
- 入口类型：用户界面
- 验证动作：以提交人身份创建一个工单（填写主题、描述、分类，选择优先级 P2），提交后打开该工单详情查看。
- 预期结果：工单详情显示系统生成的工单ID、所填主题/描述/分类/P2 优先级、提交人姓名与邮箱、创建时间，且工单处于初始状态"创建"。
- 证据类型：runtime-render, session-persistence

### AC-02：工单支持多轮回复并记录回复人与回复时间
- 验收条件：同一工单可进行多轮回复；每条回复记录回复人与回复时间，可按时间顺序读回。
- 入口类型：用户界面
- 验证动作：对同一工单，由提交人与处理方两个不同回复人先后各发送至少两条回复，然后查看该工单的回复列表。
- 预期结果：全部回复按回复时间顺序展示，每条回复显示回复人、回复时间与回复内容。
- 证据类型：runtime-render, session-persistence

### AC-03：工单生命周期状态流转
- 验收条件：工单状态按"创建 → 待分配 → 待处理 → 完成"流转，并支持进入"取消"终态；每次状态变化在工单上可观察。
- 入口类型：用户界面
- 验证动作：创建一个工单，依次完成分配到业务组、处理完成两步操作，逐步观察工单状态；另创建一个工单，在处理完成前执行取消操作。
- 预期结果：第一个工单状态依次呈现待分配/待处理，完成处理后为"完成"；第二个工单状态为"取消"，且不再进入处理流程。
- 证据类型：runtime-render, interaction

### AC-04：公司可管理多个业务组及其成员
- 验收条件：可为公司添加多个业务组，并为每个业务组设置成员；配置结果可通过列表查看读回。
- 入口类型：用户界面
- 验证动作：为公司 A 添加两个业务组（如"网络组"、"软件组"），分别向两个业务组添加成员，然后查看公司 A 的业务组列表。
- 预期结果：公司 A 下可见两个业务组，且每个业务组展示其成员。
- 证据类型：runtime-render, session-persistence

### AC-05：工单按分类自动分配到业务组
- 验收条件：公司配置"分类 → 业务组"自动分配规则后，该公司新建该分类的工单会自动分配到对应业务组并进入"待处理"。
- 入口类型：用户界面
- 验证动作：为公司 A 配置分类"网络问题"→"网络组"的自动分配规则，以公司 A 提交人身份创建分类为"网络问题"的工单，随后查看该工单。
- 预期结果：该工单被分配到"网络组"（工单上可见所属业务组），状态为"待处理"。
- 证据类型：runtime-render, session-persistence

### AC-06：工单支持转派
- 验收条件：处于"待处理"的工单可转派给其他处理方；转派后工单处理方变更，工单仍处于"待处理"并可继续处理。
- 入口类型：用户界面
- 验证动作：处理人打开一个"待处理"工单，执行转派到另一业务组的成员，随后查看该工单的当前处理方。
- 预期结果：工单当前处理方变更为被转派对象，状态仍为"待处理"，且转派操作可追溯（显示转派人与转派时间）。
- 证据类型：runtime-render, interaction

### AC-07：处理工单时可查看提交人完整信息
- 验收条件：处理人处理工单时，可查看提交人的姓名、公司、部门及历史工单。
- 入口类型：用户界面
- 验证动作：处理人打开一个"待处理"工单，查看提交人信息区域及该提交人的历史工单列表。
- 预期结果：页面显示提交人姓名、公司、部门，并列出该提交人的历史工单（包含其此前创建的工单）。
- 证据类型：runtime-render, session-persistence

### AC-08：处理完成后记录处理信息
- 验收条件：工单处理完成后，系统记录处理人、处理时间与工单状态。
- 入口类型：用户界面
- 验证动作：处理人对一个"待处理"工单执行完成处理操作，随后查看该工单的状态与处理记录。
- 预期结果：工单状态为"完成"，处理记录显示处理人与处理时间。
- 证据类型：runtime-render, session-persistence

### AC-09：工单完成后提交人可进行满意度评价
- 验收条件：工单完成后，提交人可对该工单进行满意度评价，评价结果可读回。
- 入口类型：用户界面
- 验证动作：提交人打开一个已完成工单，提交满意度评价，随后再次查看该工单。
- 预期结果：该工单上显示提交人提交的满意度评价结果。
- 证据类型：runtime-render, session-persistence
