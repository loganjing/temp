# 系统设计

工单系统（wi-t1000007）架构基线。本文只给出承载已批准需求所必需的技术结论；产品范围、业务规则与验收语义以批准的需求基线为唯一来源，本文不重复。

<!-- system-design: scope -->
## 1. 整体方案与设计基线

### 1.1 技术栈与运行形态

| 维度 | 决策 |
| --- | --- |
| 语言 | TypeScript（前后端同构，共享类型定义） |
| 后端 | Node.js + Hono，`@hono/node-server` 单进程提供 `/api/*` |
| 前端 | React + Vite SPA（TypeScript），桌面 Web 优先 |
| 存储 | SQLite 文件数据库（`better-sqlite3`，WAL 模式），版本化 SQL 迁移 |
| 依赖安装 | npm（`package-lock.json`） |
| 形态 | 生产：单 Node 进程同时提供 API 与前端构建产物；开发：Vite 开发服务器独立端口并把 `/api` 代理到后端 |

选择依据：需求要求服务端权威数据、公司级数据隔离、跨用户共享的业务组与分配规则、工单完成触发的外部邮件通知，以及服务端统一记录的操作日志。这些能力无法由浏览器本地存储承载，因此采用「Hono + React/Vite」全栈形态。工作区当前为空项目，无既有技术栈需要沿用，也无证据支持引入额外的 CommonApp 模块或数据库以外的中间件。

### 1.2 数据权威与隔离基线

- **唯一权威来源**：服务端 SQLite。所有工单、回复、转派、评价、日志、业务组与分配规则、通知出站记录均以服务端记录为准；前端只做展示与交互提交，不缓存权威业务数据。
- **公司隔离在服务端执行**：请求进入 API 层后，先解析当前操作者身份，再以其所属公司作为强制过滤条件参与每一次查询与写入校验。前端传入的 `companyId` 仅作为公司维度筛选的输入，且必须与操作者可见范围求交，不能扩大可见范围。
- **越界的可观察结果**：公司范围外的工单不在列表、工作台与统计结果中出现；直接按 ID 访问时返回不可见结果（HTTP 404 语义），不返回其主题、回复、评价或日志内容；越界写操作被拒绝并返回可见错误。
- **提交人信息与提交人公司**：工单所属公司取自提交人所属公司（来自需求基线的默认约定），落库时固化在工单上，使隔离过滤与按公司统计不依赖用户表随时间的变动。

### 1.3 身份与操作者上下文

需求未规定角色权限模型与配置入口的授权方式，因此本设计只实现闭合隔离与"操作人可记录"所需的最小身份机制，不引入权限矩阵：

- 系统内置用户目录（姓名、邮箱、公司、部门），用户是提交人、处理人、业务组配置者的统一载体。
- 会话由安全的 HttpOnly Cookie 承载操作者标识；前端提供操作者选择/登录入口以便在同一浏览器中切换公司身份进行验证。
- 能力守卫按角色区分"提交人能力 / 处理人能力 / 配置能力"，只用于让对应界面与接口对不合适身份给出明确拒绝反馈；细粒度授权留待后续需求明确后扩展，不构成本次验收条件。

### 1.4 全局 UI 基线

| 维度 | 结论 |
| --- | --- |
| 应用/业务模板 | `helpdesk`（依据：工单受理、派发、处理与评价闭环） |
| 展示模板 ID | `split-master-detail`（依据：核心动作是逐条处理工单，列表/队列与当前记录详情需协同） |
| 视觉风格 | Modern SaaS（通用业务后台默认值） |
| 设计 Token 方向 | 柔和中性底色、细边界、少阴影、中等圆角、清晰无衬线字体；一个主色 + 语义状态色；动效短且承担反馈作用 |
| 应用壳 | 左侧主导航 + 顶部上下文栏 + 主工作区 |
| 导航分区 | 工单工作台、工单列表、业务组与分配规则配置、统计与分析仪表盘 |
| 主工作流布局 | 工作台/列表为左侧队列区（筛选、搜索、排序工具栏 + 表格或列表），右侧为当前工单详情区（信息、回复线程、处理动作、转派记录、日志）；配置与统计页面为主工作区全宽布局 |
| 目标设备 | 桌面 Web 优先；不设计移动端/窄屏专用布局（需求未要求该范围） |

关键全局状态：

- **加载**：列表与详情分区各自局部加载态，切换工单不阻塞整体界面。
- **空态**：无工单、无回复、无分配规则、无评价、无日志、无统计数据时给出空态说明与下一步引导。
- **错误**：接口失败显示可读错误并保留重试入口；表单校验错误就地提示。
- **无权限/不可见**：公司范围外资源不展示且不返回内容，直达链接给出"资源不存在或不可见"的一致提示，不泄露存在性之外的信息。
- **成功**：创建、回复、转派、完成、取消、评价、配置保存成功后给出简短反馈，并就地刷新受影响的数据区域。
- **被拒绝的业务流转**：对终态工单的回复/转派/完成/取消、重复评价、未完成工单评价等，返回明确拒绝原因并保持状态不变。

### 1.5 系统关系概览

```
[浏览器 SPA]
   |  fetch /api/*（Cookie 会话）
   v
[Hono API 层]  身份解析 · 入参校验 · 公司范围求交 · 统一错误与日志
   |
   +--> [领域服务] ticket · assignment · collaboration · notification · statistics
   |        |
   |        +--> [仓储/迁移层] SQLite（WAL，版本化 SQL 迁移）
   |
   +--> [通知出站] email_outbox 记录 + 可替换发送通道（默认本地出站记录，可选 SMTP）
```

## 2. 领域责任、模块边界与接口摘要

模块只通过公开服务能力协作；各模块的私有表结构不在其他模块中直接读写。字段级定义（路径、请求/响应字段、类型、可空性、错误码、幂等性）以 `technical-contract.md` 为唯一来源，本节只保留接口摘要与调用方向。

### 2.1 Web 前端（SPA）

- **职责**：渲染工作台、工单列表与详情、提交表单、配置页、统计仪表盘；管理筛选/搜索/排序的视图状态；展示服务端返回的可见数据与业务拒绝反馈。
- **事实归属**：不拥有任何业务事实，只持有当前界面的视图状态与表单草稿。
- **调用方向**：单向调用 HTTP API 层，不直连数据库、不实现业务规则判定。

### 2.2 HTTP API 层

- **职责**：解析会话身份；校验入参；把操作者公司范围固定为查询/写入的强制约束；把领域错误映射为一致的 HTTP 语义与可读消息；请求结束时更新受影响的日志与通知出站。
- **事实归属**：无独立业务表；会话 Cookie 是身份事实的载体。
- **调用方向**：调用领域服务，不直接拼装 SQL。

接口摘要（全部挂在 `/api` 前缀下）：

| 接口 | 用途 | 调用方向 |
| --- | --- | --- |
| `GET /session`、`POST /session` | 读取当前操作者上下文 / 切换操作者身份以支持多公司验证 | SPA → API |
| `POST /tickets` | 受理新工单：生成工单 ID、落库提交人信息与创建时间，并触发自动分配 | SPA → API → ticket + assignment |
| `GET /tickets` | 工单列表查询：关键字搜索、按分类/优先级/状态筛选、按创建时间排序、公司维度筛选 | SPA → API → ticket |
| `GET /tickets/{id}` | 工单详情（含回复线程、分配结果、转派记录、处理结果、评价） | SPA → API → ticket |
| `POST /tickets/{id}/replies` | 追加一轮回复，记录回复人与回复时间 | SPA → API → ticket |
| `POST /tickets/{id}/transfer` | 转派到本公司范围内的业务组或成员 | SPA → API → collaboration |
| `POST /tickets/{id}/complete` | 完成处理，记录处理人与处理时间并触发完成通知 | SPA → API → ticket + notification |
| `POST /tickets/{id}/cancel` | 取消工单（受状态规则约束） | SPA → API → ticket |
| `POST /tickets/{id}/rating` | 提交满意度评分（每单一次） | SPA → API → ticket |
| `GET /tickets/{id}/logs` | 读取该工单的操作记录 | SPA → API → ticket |
| `GET /users/{id}/profile` | 提交人完整信息（姓名、公司、部门）与历史工单 | SPA → API → ticket |
| `GET /business-groups`、`POST /business-groups`、`PUT /business-groups/{id}/members` | 业务组与成员的配置与读回 | SPA → API → assignment |
| `GET /assignment-rules`、`POST /assignment-rules`、`PUT /assignment-rules/{id}` | 「分类 → 业务组」自动分配规则的配置与读回 | SPA → API → assignment |
| `GET /stats/distribution` | 按公司或部门维度的工单数量分布 | SPA → API → statistics |
| `GET /stats/dashboard` | 工单量、平均响应时间、满意度、热点问题 | SPA → API → statistics |
| `GET /notifications` | 读取完成通知的发送记录（用于核对面向提交人邮箱的发送结果） | SPA/校验 → API → notification |

### 2.3 工单模块（ticket）

- **职责**：工单的创建、读取、回复、状态流转校验、完成与取消、提交人资料与历史工单聚合、工单操作日志写入。工单状态机（创建、待分配、待处理、完成、取消）与拒绝规则的实现归属本模块。
- **唯一事实归属**：工单主记录、回复记录、评价记录、操作日志表。
- **接口摘要**：`createTicket`、`listTickets`、`getTicket`、`addReply`、`completeTicket`、`cancelTicket`、`submitRating`、`getSubmitterProfile`、`listTicketLogs`。
- **调用方向**：被 API 层调用；创建路径调用 `assignment.autoAssign`；完成路径调用 `notification.enqueueCompletionNotice`；状态变更统一经 `appendLog`。

### 2.4 分配模块（assignment）

- **职责**：业务组与成员配置；「分类 → 业务组」规则配置与匹配；工单提交时的自动分配判定与结果落库（目标业务组、分配时间、分配方式）。
- **唯一事实归属**：业务组、业务组成员、自动分配规则表；分配结果字段写入工单主记录。
- **接口摘要**：`listBusinessGroups`、`createBusinessGroup`、`setGroupMembers`、`listAssignmentRules`、`upsertAssignmentRule`、`autoAssign(ticket)`、`assignManually(ticket, target)`。
- **调用方向**：被 API 层与工单模块调用；只根据本公司规则与工单分类判定，不读取其他公司配置。
- **判定约定**：自动分配在工单创建流程内同步完成；命中启用规则时工单归属该业务组并进入待处理，未命中时保持待分配。

### 2.5 协作模块（collaboration）

- **职责**：转派操作：校验目标属于同一公司范围、更新工单当前处理方（业务组/成员）、记录转派人、转派时间与转派目标；转派后状态保持待处理。
- **唯一事实归属**：转派记录表。
- **接口摘要**：`listTransferTargets(ticket)`、`transferTicket(ticket, target)`。
- **调用方向**：被 API 层调用，经工单模块校验状态与写入日志。

### 2.6 通知模块（notification）

- **职责**：生成面向提交人邮箱的完成通知并通过可替换的发送通道投递；持久化发送记录（收件人邮箱、工单 ID、状态、时间）使"完成动作触发了通知发送"可核对；投递失败不改变工单完成结果，但失败状态可读回。
- **唯一事实归属**：通知出站记录表。
- **接口摘要**：`enqueueCompletionNotice(ticket)`、`listNotifications(filter)`、`flushOutbox()`。
- **调用方向**：被工单模块的完成路径调用；发送通道适配器为本地出站记录（默认）或 SMTP（通过环境变量启用）。

### 2.7 统计模块（statistics）

- **职责**：按公司、部门维度的工单数量分布；运营指标计算：工单量、平均响应时间、满意度、热点问题。
- **唯一事实归属**：无自有表；以只读方式聚合工单、回复与评价数据。
- **接口摘要**：`getDistribution(dimension)`、`getDashboard()`。
- **调用方向**：被 API 层调用；统计范围强制限定为操作者可见的公司范围，不提供跨公司汇总。
- **口径实现**：平均响应时间 = 有处理方回复的工单「创建时间 → 首次处理方回复时间」时长均值（无处理方回复的工单不计入）；满意度 = 已评价工单评分均值；热点问题 = 按问题分类的工单量降序取前列。

### 2.8 访问控制（access-control，纵向能力）

- **职责**：解析操作者身份、派生其公司范围、为查询与写入提供强制过滤与越界拒绝；提供角色能力守卫。
- **事实归属**：用户与公司目录表。
- **接口摘要**：`resolveOperator(request)`、`scopedCompanyFilter(operator, requested)`、`assertVisible(operator, entity)`、`assertCapability(operator, capability)`。
- **调用方向**：由 API 层在最前调用，领域模块通过其返回值获得已确定的作用域，不各自实现过滤逻辑。

### 2.9 数据访问与迁移层

- **职责**：SQLite 连接管理（创建父目录、WAL、外键约束）、版本化 SQL 迁移的执行与版本记录、仓储查询封装。
- **唯一事实归属**：迁移版本表。
- **调用方向**：被各领域模块调用；不向上暴露业务规则。

## 3. 数据模型与迁移

- **存储形态**：单文件 SQLite 数据库。默认路径 `./data/ticket.sqlite`；打开连接前创建其父目录，使干净目录无需人工准备即可运行。WAL 模式与外键约束在连接初始化时启用。
- **迁移方式**：`migrations/` 下按序编号的 `.sql` 文件，启动时在事务内按版本表记录逐步应用，已应用版本不重复执行；不使用 ORM 自动同步，不手工改 schema。新增或变更表结构一律追加新迁移。
- **隔离测试数据库**：验证时通过 `DB_PATH` 覆盖为独立文件（如 `./data/test-<pid>.sqlite`），验证结束只清理本次创建的数据库文件与进程。

核心关系（字段级定义见 `technical-contract.md`）：

| 实体 | 归属与关键关系 |
| --- | --- |
| 公司 `company` | 顶层隔离边界 |
| 用户 `app_user` | 属于一个公司，携带姓名、邮箱、部门；是提交人/处理人/配置者的统一载体 |
| 业务组 `business_group` | 属于一个公司；一个公司可有多个业务组 |
| 业务组成员 `business_group_member` | 业务组与用户的多对多关联 |
| 自动分配规则 `assignment_rule` | 属于一个公司，关联「问题分类 → 业务组」，可启用/停用 |
| 工单 `ticket` | 属于一个公司，引用提交人；携带主题、描述、分类、SLA 优先级（P0–P4）、状态、当前处理方（业务组/成员）、分配结果（目标业务组、分配时间、分配方式）、处理结果（处理人、处理时间）、取消时间 |
| 回复 `ticket_reply` | 属于工单，记录回复人、回复时间、内容；工单与回复一对一归属，用于多轮回复与首次处理方回复的时序计算 |
| 转派 `ticket_transfer` | 属于工单，记录转派人、转派时间、原/目标处理方 |
| 评价 `ticket_rating` | 与工单一对一（唯一约束保证每单一次），记录评价人、评价时间、1–5 分 |
| 操作日志 `operation_log` | 属于工单，记录操作类型、操作人、操作时间、工单 ID 及必要上下文 |
| 通知出站 `email_outbox` | 属于工单，记录收件人邮箱、主题、投递状态与时间 |

一致性约定：

- 工单创建与自动分配在同一事务内完成：工单主记录、分配结果、创建与分配日志（命中规则时）一并提交，避免出现"已分配但无日志"或"有日志但未分配"的中间态。
- 完成动作在同一事务内更新工单状态与处理结果并写入完成日志；通知出站记录在同一事务内入队，随后投递，投递结果异步回写状态，投递失败不回滚工单完成。
- 回复、转派、评价、取消各自在事务内完成业务写入与对应日志写入。
- 所有时间戳由服务端生成并统一为 UTC 存储，展示层按本地时区格式化。

## 4. 外部集成：完成通知邮件

- **依赖性质**：需求明确要求工单完成时向提交人邮箱发送通知，邮件服务与模板未规定，因此设计为可替换的发送通道，并把"发送记录"作为可观察结果。
- **通道适配器**：接口 `MailChannel`，方法 `send({ to, subject, body, ticketId })`。默认实现为本地出站记录通道：把通知写入 `email_outbox` 并标记为已发送（演示/验证环境下可核对收件人邮箱与工单归属）；当配置了 SMTP 相关环境变量（主机、端口、账号、发件人）时切换到 SMTP 通道，真实投递并回写状态。
- **失败可见性**：投递失败时 `email_outbox` 保留失败状态与错误摘要，工单完成结果不受影响；失败通知可重试（`flushOutbox`）。
- **幂等性**：同一工单的完成通知按工单 ID 去重，重复触发不会产生多条"完成通知"记录。
- **边界**：通知只发往提交人邮箱；不引入其他外部系统。

## 5. 运行与验证

- **安装**：`npm install`
- **启动入口**：`npm start`（构建后运行 Node 服务；后端监听 `PORT`，默认 `8787`，并在同一进程提供前端静态产物）；开发入口 `npm run dev`（Vite 开发服务器 + 后端进程，Vite 将 `/api` 代理到后端）。
- **前端开发地址**：Vite 默认端口（可用 `VITE_PORT` 覆盖），后端地址由代理配置指向 `PORT`。
- **数据库位置**：默认 `./data/ticket.sqlite`；测试用 `DB_PATH` 覆盖，文件数据库的父目录在打开前自动创建。
- **验收命令**：`npm run verify`（独立于启动入口的验收脚本）。该脚本自行选择空闲端口启动隔离实例、等待真实监听就绪、使用独立的 `DB_PATH`、在结束时只清理本次启动的进程与数据库文件；因此无需额外后台启动服务或手工准备环境。
- **初始数据**：首次启动执行迁移后可加载演示数据（多公司、多部门、用户、业务组、分配规则与示例工单），使各界面无需人工准备即可呈现非空状态；演示数据加载可关闭。

## 6. 架构决策

- **ADR-1 采用 Hono + React/Vite 全栈而非纯前端**：公司隔离、跨用户共享配置、外部邮件通知与服务端统一日志都要求服务端权威数据；纯浏览器存储无法承载多操作者可见范围与不可篡改的操作人记录。影响：需要一个后端进程与数据库运行环境。
- **ADR-2 以 SQLite 文件库作为权威存储**：需求未规定性能与部署要求，也无证据支持引入独立数据库服务；SQLite 单文件便于干净环境直接运行与隔离验证，且支持版本化迁移。影响：如需高并发或集中部署需后续替换为服务型数据库，迁移路径由版本化迁移保留。
- **ADR-3 公司隔离在服务端强制求交，而非依赖前端过滤**：隔离是安全属性，前端过滤可被绕过；将操作者公司固定为查询/写入的强制条件，越界返回不可见结果而非可区分错误，避免泄露存在性之外的信息。影响：所有新增查询必须经访问控制模块派生作用域。
- **ADR-4 通知通过可替换通道出站记录实现**：需求只要求"完成动作触发面向提交人邮箱的通知发送"这一可观察结果，未规定邮件服务；出站记录让结果可核对且不把外部可用性绑定为完成前置条件。影响：生产投递需提供 SMTP 配置，失败以出站状态而非工单状态体现。
- **ADR-5 自动分配同步在创建流程内完成**：使"提交后即为待处理"可立即观察，避免异步延迟带来的状态歧义。影响：规则匹配失败或未配置时工单落为待分配，不做重试或后台补偿（需求未要求）。
- **ADR-6 最小身份机制而非完整权限矩阵**：需求明确将角色权限模型与配置入口授权列为未规定项；只实现隔离与操作人记录所需的最小身份，避免为未规定的语义创造验收面。影响：后续若明确权限模型，在访问控制模块的能力守卫上扩展。

## 7. 未决事项与残余风险

- 跨公司可见范围（如平台级支持人员）未在需求中规定，本设计按"仅本公司可见"实现，并在访问控制模块预留统一的作用域派生入口以便后续扩展。
- 邮件真实投递依赖运行环境提供 SMTP 配置；无配置时使用本地出站记录通道，其发送结果属于平台内可观察记录，不等同于外部邮件服务已投递。
- 分类字典与 SLA 时限清单未规定，设计以可配置的分类字符串与 P0–P4 枚举承载，不内置具体时限规则。
