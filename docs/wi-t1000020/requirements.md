# 访客系统（k03-guest）需求

## 1. 目标

为访客提供一套基于微信小程序的来访登记与审批系统。访客通过小程序登记来访信息并提交审核；审批人员通过移动端审批系统对待来访人员进行审核（通过或拒绝）。登记信息持久化到后端数据库，访客可在小程序中查看自己的登记状态与审核结果。

> 来源标注：本节目标由用户明确提出。

## 2. 角色与入口

| 角色 | 入口 | 说明 |
| --- | --- | --- |
| 访客 | 微信小程序 | 登记来访信息、查看审核状态 |
| 审批人 | 移动端审批系统（适配移动端） | 审核待来访访客、给出通过/拒绝结果 |

> 来源标注：访客与小程序入口由用户明确提出；审批人及其移动端审批入口由用户「需要审批后端系统，可以审核到来的人员，审核系统要适配移动端」明确要求。用户未指定审批人的具体身份、授权方式与权限范围，标记为未规定。

## 3. 核心流程

### 3.1 访客登记与状态查看

1. 访客在微信小程序打开访客登记页。
2. 系统尝试从微信获取访客手机号；获取不到时，访客手工填写手机号。
3. 访客填写其余必填字段并提交登记。
4. 系统将登记信息写入后端数据库，登记记录进入「待审核」状态。
5. 访客可在小程序中查看自己已提交登记的当前状态与审核结果。

### 3.2 审批处理

1. 审批人在移动端审批系统查看待审核访客列表。
2. 审批人查看访客登记详情，对来访人员进行审核，结果为「通过」或「拒绝」。
3. 审核结果写回后端，访客登记状态随之更新。
4. 访客在小程序中可看到更新后的状态。

> 来源标注：上述流程由用户明确要求的能力（登记、数据库记录、审批、移动端适配）闭合为端到端可验收流程；状态名称「待审核/通过/拒绝」为推荐基线，用于使审核结果可观察、可回看，可由用户调整。

## 4. 访客信息字段

| 字段 | 必填 | 来源标注 | 说明 |
| --- | --- | --- | --- |
| 手机号 | 是 | 用户明确提出 | 可从微信获取；获取不到时手工填写 |
| 身份证号 | 是 | 用户明确提出 | — |
| 公司信息 | 是 | 用户明确提出 | 访客所在公司 |
| 人名 | 是 | 用户明确提出 | 访客姓名 |
| 访问事由 | 是 | 用户明确提出 | 来访目的说明 |
| 被访人 | 否 | 推荐基线 | 使审批人可联系或确认接待对象；用户未明确要求，可调整或移除 |
| 预计到访时间 | 否 | 推荐基线 | 帮助审批人判断来访时效；用户未明确要求，可调整或移除 |

> 来源标注：用户明确授权「其他的你可以发挥」，故在被访人、预计到访时间等与核心审批直接相关、可逆、可观察的必要缺口上给出最小推荐基线；这些为候选补充，不属于用户已确认基线，用户可调整或移除。用户未指定字段格式校验规则（如身份证号校验位、手机号正则），标记为未规定，实现时可按通用合法性校验处理。

## 5. 审批系统适配

- 审批系统适配移动端：审批列表与详情页在移动端设备上可用、可操作（查看列表、查看详情、执行通过/拒绝）。
> 来源标注：由用户明确提出。用户未指定审批系统的具体载体（独立小程序/Web/管理后台）、登录与权限方案，标记为未规定。

## 6. 数据持久化

- 访客登记信息与审核结果由后端写入数据库持久化记录；提交成功后可通过相应读取行为读回。
> 来源标注：用户明确提出「需要记录到数据库」「小程序本身要有后端和数据库去记录访客人员」。用户未指定数据库类型、存储技术与部署方式，标记为未规定。

## 7. 未规定事项

以下事项用户未明确，不纳入当前基线，实现时按合理默认处理或后续确认：

- 审批人的身份认定、登录方式与权限分配方案。
- 审批系统的具体产品载体（独立小程序、Web 后台等）。
- 数据库与后端技术选型、部署环境。
- 字段格式校验的精确规则（身份证校验位、手机号正则等）。
- 通知方式（审核结果是否主动推送给访客/审批人）。
- 登记记录的保留期限与导出能力。

## 8. 验收场景

### AC-01：访客可在微信小程序完成来访登记并持久化

- 验收条件：访客在微信小程序登记页完成必填信息填写并提交，系统将登记信息持久化到后端数据库，登记记录可被读回且状态为待审核。
- 入口类型：用户界面
- 验证动作：访客在小程序登记页尝试从微信获取手机号（获取不到时手工填写手机号），填写身份证号、公司信息、人名、访问事由后提交登记。
- 预期结果：提交成功；后端数据库可读回包含上述必填字段的完整登记记录；该记录状态为「待审核」。
- 证据类型：interaction,runtime-render,session-persistence
- 共享流程组：访客登记

### AC-02：访客可在小程序查看登记状态与审核结果

- 验收条件：访客提交登记后，可在小程序中查看自己已提交登记的当前状态；当审批结果变化时，访客可见更新后的状态。
- 入口类型：用户界面
- 验证动作：访客提交一条登记后，在小程序查看该登记的状态；随后该登记被审批人处理（通过或拒绝），访客再次查看状态。
- 预期结果：首次查看状态为待审核；审批处理后，访客再次查看可见状态更新为通过或拒绝。
- 证据类型：interaction,session-persistence
- 共享流程组：访客登记

### AC-03：审批人可在移动端审批系统对待审核访客进行审核

- 验收条件：审批人在移动端审批系统查看待审核访客列表，查看访客登记详情，并对其执行通过或拒绝，审核结果写入后端。
- 入口类型：用户界面
- 验证动作：审批人在移动设备上打开审批系统，查看待审核列表，进入某条访客登记详情，执行通过（或拒绝）。
- 预期结果：待审核列表中该访客登记消失或状态变更；后端记录该登记审核结果为通过（或拒绝）。
- 证据类型：interaction,runtime-render,session-persistence
- 共享流程组：审批处理

### AC-04：审批系统在移动端可用且可操作

- 验收条件：审批系统的列表与详情页在移动端设备屏幕上可正常浏览、可点击操作（查看列表、查看详情、执行通过/拒绝）。
- 入口类型：用户界面
- 验证动作：在移动端设备（或移动端视口）打开审批系统，浏览待审核列表，进入详情并执行一次审核操作。
- 预期结果：列表与详情在移动端可见且布局可操作；通过/拒绝操作可正常完成。
- 证据类型：interaction,visual-style
- 共享流程组：审批处理
