# 工单系统需求文档（T1000487）

## 1. 目标与范围

构建一个工单管理系统，支持工单从创建到完成的完整生命周期管理，包括工单分配、协作转派、处理跟踪和用户评价。

**用户明确提出的需求范围：**
- 工单基本信息管理（ID、主题、描述、分类、提交人信息含邮箱、创建时间）
- 工单多轮回复
- SLA 优先级（P0–P4）和问题分类
- 工单生命周期状态（创建、待分配、待处理、完成、取消）
- 工单分配：公司下多业务组，按分类自动分配
- 工单协作：转派操作
- 工单处理：查看提交人完整信息，记录处理人/处理时间/状态
- 用户评价：满意度评价

**未规定事项（不在本阶段决定）：**
- 具体技术架构、数据库选型、存储方案
- 用户认证与权限体系细节（用户仅提及"提交人信息含邮箱"，未规定登录/注册流程）
- 具体页面布局与产品载体（用户描述了人机操作入口，标注为用户界面入口）

## 2. 角色

| 角色 | 说明 | 来源 |
|------|------|------|
| 提交人 | 创建工单的用户，需提供姓名、公司、部门、邮箱等信息 | 用户明确提出 |
| 处理人 | 业务组成员，负责处理分配到所属业务组的工单 | 用户明确提出 |
| 系统自动分配 | 根据分类规则自动将工单分配到对应业务组 | 用户明确提出 |

> 用户未明确提出管理员角色。公司、业务组、成员的维护操作（增删改）由谁执行未规定，保持开放。

## 3. 核心实体

### 3.1 工单（Ticket）

工单包含以下信息（用户明确提出）：

| 属性 | 说明 |
|------|------|
| 工单ID | 唯一标识 |
| 主题 | 工单标题 |
| 描述 | 工单详细内容 |
| 分类 | 问题分类，用于自动分配规则 |
| SLA优先级 | P0、P1、P2、P3、P4 |
| 提交人信息 | 姓名、公司、部门、邮箱 |
| 创建时间 | 工单创建的时间戳 |
| 状态 | 当前生命周期状态 |
| 当前业务组 | 工单当前分配到的业务组（分配后） |
| 处理人 | 实际处理该工单的人员（处理后记录） |
| 处理时间 | 工单完成处理的时间 |
| 评价 | 用户提交的满意度评价（完成后） |

### 3.2 回复（Reply）

工单支持多轮回复（用户明确提出）：

| 属性 | 说明 |
|------|------|
| 回复内容 | 回复的具体文本 |
| 回复人 | 发起回复的人员 |
| 回复时间 | 回复的时间戳 |
| 所属工单 | 关联的工单ID |

### 3.3 公司（Company）

- 一个公司下可以有多个业务组（用户明确提出）

### 3.4 业务组（Business Group）

| 属性 | 说明 |
|------|------|
| 名称 | 业务组名称 |
| 所属公司 | 关联的公司 |
| 成员 | 业务组中的处理人员列表 |

### 3.5 分配规则（Assignment Rule）

用户明确提出：允许某个公司的工单按照分类自动分配到某个业务组。

| 属性 | 说明 |
|------|------|
| 所属公司 | 规则适用的公司 |
| 问题分类 | 触发规则匹配的工单分类 |
| 目标业务组 | 匹配后分配到的业务组 |

### 3.6 评价（Evaluation）

用户明确提出：用户收到工单后进行满意度评价。

| 属性 | 说明 |
|------|------|
| 满意度评分 | 用户给出的满意度评分 |
| 关联工单 | 评价对应的工单 |

> 用户未规定满意度评分的具体标度（如1-5星、百分制等），保持开放。

## 4. 工单生命周期

用户明确提出的工单状态及流转：

```
创建 → 待分配 → 待处理 → 完成
  ↓                 ↓
 取消              取消
```

| 状态 | 说明 | 触发条件 |
|------|------|----------|
| 创建 | 工单刚被提交 | 提交人创建工单 |
| 待分配 | 工单等待分配到业务组 | 创建后进入待分配状态 |
| 待处理 | 工单已分配到业务组，等待/正在处理 | 分配规则匹配或手动分配后 |
| 完成 | 工单处理完成 | 处理人标记完成 |
| 取消 | 工单被取消 | 手动取消操作 |

### 4.1 分配流程

1. 提交人创建工单，工单进入「待分配」状态
2. 系统根据工单所属公司 + 分类匹配分配规则
3. 若匹配到规则，工单自动分配到对应业务组，状态变为「待处理」
4. 若未匹配到规则，工单停留在「待分配」状态，等待手动分配

> 用户未规定未匹配规则时的具体处理方式。推荐基线：允许手动分配作为兜底，此为保守、可逆的最小闭合方案。

### 4.2 转派流程

用户明确提出支持工单转派操作：

1. 工单处于「待处理」状态时，当前处理人/业务组可将工单转派到其他业务组
2. 转派后工单仍保持「待处理」状态，归属变更为新业务组
3. 转派操作应记录转派来源和目标

### 4.3 评价流程

1. 工单状态变为「完成」后，提交人可对工单进行满意度评价
2. 评价结果关联到对应工单

> 用户原文为"用户收到工单后进行满意度评价"，结合工单生命周期，评价发生在工单完成后。

## 5. 功能需求

### 5.1 工单管理

**5.1.1 工单创建**
- 提交人可创建工单，填写主题、描述、分类、SLA优先级（P0–P4）
- 提交人信息（姓名、公司、部门、邮箱）随工单一并记录
- 创建时记录创建时间，工单状态为「创建」，随后进入「待分配」

**5.1.2 工单回复**
- 工单支持多轮回复
- 每条回复记录回复人和回复时间
- 回复关联到对应工单

**5.1.3 SLA优先级与分类**
- 工单创建时可设置SLA优先级（P0、P1、P2、P3、P4）
- 工单创建时可设置问题分类，分类用于自动分配规则匹配

**5.1.4 工单状态管理**
- 工单状态遵循生命周期：创建 → 待分配 → 待处理 → 完成 / 取消
- 状态变更需可观察

### 5.2 工单分配

**5.2.1 公司与业务组管理**
- 允许给某个公司增加多个业务组
- 每个业务组可以设置成员

**5.2.2 自动分配规则**
- 允许配置规则：某个公司的工单按照分类自动分配到某个业务组
- 工单进入「待分配」状态后，系统根据公司+分类匹配规则进行自动分配
- 匹配成功后工单分配到目标业务组，状态变为「待处理」

### 5.3 工单协作

**5.3.1 工单转派**
- 工单处于「待处理」状态时支持转派操作
- 转派可将工单从当前业务组转移到其他业务组
- 转派后工单归属变更，状态保持「待处理」

### 5.4 工单处理

**5.4.1 提交人信息查看**
- 处理工单时可查看提交人的完整信息，包括：
  - 姓名
  - 公司
  - 部门
  - 历史工单（该提交人此前提交的所有工单）

**5.4.2 处理记录**
- 工单处理后，记录以下信息：
  - 处理人
  - 处理时间
  - 工单状态

### 5.5 用户评价

**5.5.1 满意度评价**
- 工单完成后，用户可对工单进行满意度评价
- 评价关联到对应工单

## 6. 验收场景

### AC-01：提交人可创建工单并记录完整信息
- 验收条件：提交人创建工单后，工单包含ID、主题、描述、分类、SLA优先级、提交人信息（姓名、公司、部门、邮箱）和创建时间，工单进入待分配状态。
- 入口类型：用户界面
- 验证动作：提交人填写工单主题、描述、分类、SLA优先级并提交创建。
- 预期结果：工单创建成功，所有填写信息可读回，创建时间被记录，工单状态为待分配。
- 证据类型：interaction, runtime-render, session-persistence

### AC-02：工单支持多轮回复
- 验收条件：工单创建后，不同人员可对同一工单进行多轮回复，每条回复记录回复人和回复时间，所有回复关联到该工单。
- 入口类型：用户界面
- 验证动作：对已存在工单连续发起多条回复。
- 预期结果：所有回复均可读回，每条回复包含回复人和回复时间，回复按时间顺序关联到该工单。
- 证据类型：interaction, session-persistence

### AC-03：工单SLA优先级和分类可设置
- 验收条件：创建工单时可设置SLA优先级（P0–P4）和问题分类，设置后可通过读取工单信息确认。
- 入口类型：用户界面
- 验证动作：创建工单时选择SLA优先级和问题分类。
- 预期结果：工单保存后，优先级和分类字段可读回，值与设置一致。
- 证据类型：interaction, session-persistence

### AC-04：公司可创建多个业务组并设置成员
- 验收条件：给某个公司增加多个业务组后，每个业务组可设置成员，业务组和成员信息可读回。
- 入口类型：用户界面
- 验证动作：为公司创建多个业务组，并为每个业务组添加成员。
- 预期结果：每个业务组及其成员列表均可读回，业务组数量和成员关系与设置一致。
- 证据类型：interaction, session-persistence

### AC-05：工单按分类自动分配到业务组
- 验收条件：配置某公司按分类自动分配到业务组的规则后，该公司下创建的工单按分类匹配规则，自动分配到对应业务组，工单状态变为待处理。
- 入口类型：用户界面
- 验证动作：配置公司A的分类X自动分配到业务组Y的规则，然后创建公司A下分类为X的工单。
- 预期结果：工单创建后自动分配到业务组Y，状态从待分配变为待处理，当前业务组为Y。
- 证据类型：interaction, session-persistence

### AC-06：工单可转派到其他业务组
- 验收条件：处于待处理状态的工单可转派到其他业务组，转派后工单归属变更为目标业务组，状态保持待处理。
- 入口类型：用户界面
- 验证动作：对待处理状态的工单执行转派到另一业务组的操作。
- 预期结果：工单当前业务组变更为目标业务组，状态仍为待处理，转派操作可追溯。
- 证据类型：interaction, session-persistence

### AC-07：处理工单时可查看提交人完整信息含历史工单
- 验收条件：处理工单时可查看提交人的姓名、公司、部门和该提交人的历史工单列表。
- 入口类型：用户界面
- 验证动作：打开待处理工单的处理界面，查看提交人信息区域。
- 预期结果：页面显示提交人姓名、公司、部门，以及该提交人此前提交的历史工单列表，历史工单可查看。
- 证据类型：interaction, runtime-render

### AC-08：工单处理后记录处理人和处理时间
- 验收条件：工单处理完成后，记录处理人、处理时间和工单状态，记录信息可读回。
- 入口类型：用户界面
- 验证动作：处理人对工单执行完成处理操作。
- 预期结果：工单状态变为完成，处理人和处理时间被记录并可通过工单信息读回。
- 证据类型：interaction, session-persistence

### AC-09：工单完成后用户可进行满意度评价
- 验收条件：工单完成后，用户可对该工单进行满意度评价，评价结果关联到工单并可读回。
- 入口类型：用户界面
- 验证动作：对已完成工单提交满意度评价。
- 预期结果：评价保存成功，关联到对应工单，可通过工单信息读回评价结果。
- 证据类型：interaction, session-persistence

### AC-10：工单可取消
- 验收条件：工单在生命周期中可被取消，取消后状态变为取消。
- 入口类型：用户界面
- 验证动作：对未完成的工单执行取消操作。
- 预期结果：工单状态变为取消，状态变更可读回。
- 证据类型：interaction, session-persistence

## 7. 推荐基线

以下推荐为闭合核心目标所必需的最小补充，均为保守、可逆、可观察的方案，不代替用户决定：

| 推荐项 | 说明 | 理由 |
|--------|------|------|
| 手动分配兜底 | 当工单未匹配到自动分配规则时，允许手动将其分配到某个业务组 | 用户要求"按分类自动分配"，但未规定未匹配时的处理。不提供兜底会导致工单永久滞留在待分配状态，无法进入处理流程 |
| 转派记录 | 转派操作记录来源业务组和目标业务组 | 用户要求"支持转派操作"，转派链路可追溯是协作场景的基本闭合 |

> 满意度评分的具体标度、评价内容字段等用户未规定，保持开放，不在本阶段固定。
