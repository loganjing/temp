# 170-餐饮服务 — 需求规格

## 1. 目标

为餐饮配送场景提供机器人配送管理的完整能力，覆盖配送任务排队、多台配送机路径协调、到桌通知、任务取消和运行监控，使餐厅能够高效、安全地管理多台配送机的日常配送运作。【用户明确提出】

## 2. 角色与对象

| 对象 | 说明 |
|------|------|
| 配送机 | 执行配送任务的移动设备，具有空闲、配送中、离线等状态 |
| 桌位 | 配送目标位置，每个桌位有唯一标识 |
| 配送任务 | 一次到指定桌位的配送请求，包含目标桌位标识和配送内容 |
| 任务队列 | 管理待执行配送任务的排队结构 |

## 3. 用户旅程

### 3.1 配送任务排队与执行

1. 配送任务创建，包含目标桌位信息。
2. 任务进入等待队列，状态为待分配。
3. 有空闲配送机时，系统从队列头部取出任务并分配给该配送机。
4. 配送机规划路径并开始配送，任务状态转为配送中。
5. 多台配送机同时运行时，系统协调路径避免冲突。
6. 配送机到达目标桌位，触发到桌通知。
7. 任务标记为已送达，配送机回到空闲状态。

### 3.2 任务取消

1. 操作人员对某个任务发起取消。
2. 系统根据任务当前状态执行取消：
   - 队列中（待分配）任务：从队列移除。
   - 配送中任务：停止配送，配送机释放路径资源并恢复空闲。
3. 任务标记为已取消。

### 3.3 运行监控

1. 操作人员进入监控界面。
2. 查看队列状态：待执行任务数量及各任务详情。
3. 查看配送机状态：每台配送机的当前状态（空闲 / 配送中 / 离线）。
4. 查看异常告警信息。

## 4. 模块需求

### 4.1 配送任务队列

- **任务创建**：支持创建配送任务，任务至少包含目标桌位标识；创建后进入等待队列排队。【用户明确提出】
- **排队管理**：任务按创建顺序（FIFO）入队；新任务排在队列尾部。【用户明确提出】
- **任务分配**：当存在空闲配送机且队列中有待分配任务时，系统从队列头部取出任务分配给该配送机，任务状态从待分配转为配送中。【用户明确提出】
- **状态流转**：任务状态包括 待分配 → 配送中 → 已送达，以及从 待分配 或 配送中 → 已取消。配送机完成配送后回到空闲状态，可接受下一个任务。【推荐基线——状态流转是队列运转的必要闭合，用户未明确指定状态名，但队列功能无法在无状态定义下运作】

### 4.2 多机路径协调

- **路径冲突检测**：多台配送机同时执行配送任务时，系统检测各配送机规划路径之间的冲突。【用户明确提出】
- **冲突避免**：检测到路径冲突时，系统通过调整配送机行进顺序、等待或重新规划路径等方式避免冲突，确保多台配送机不会在同一时段占用同一路径段。【用户明确提出】
- **协调触发时机**：在任务分配并规划路径后、配送机开始行进前进行路径协调；行进过程中如出现新的冲突风险，系统持续协调。【推荐基线——用户明确要求"协调"，持续协调是确保多机安全运行的最小必要条件】

### 4.3 到桌通知

- **到达触发**：配送机到达目标桌位时，系统发送到桌通知。【用户明确提出】
- **通知内容**：通知至少包含目标桌位标识，使接收方能确认配送已到达对应桌位。【推荐基线——用户明确要求"到桌通知"，通知内容需包含桌位信息才能满足"到桌"的语义】

### 4.4 任务取消

- **取消入口**：操作人员可对队列中（待分配）或配送中状态的任务发起取消。【用户明确提出】
- **队列中取消**：待分配任务取消后，从队列移除，任务状态变为已取消。【用户明确提出】
- **配送中取消**：配送中任务取消后，配送机停止当前配送，释放已占用的路径资源并恢复空闲状态，任务状态变为已取消。【用户明确提出】
- **资源释放**：取消后释放的资源（配送机、路径）可被后续任务使用。【推荐基线——用户明确要求取消功能，资源释放是取消后的必要结果，否则取消无法达到释放运力的目的】

### 4.5 运行监控

- **队列监控**：查看当前任务队列中的待执行任务数量及各任务详情（目标桌位、当前状态）。【用户明确提出】
- **配送机监控**：查看每台配送机的当前状态（空闲 / 配送中 / 离线）。【用户明确提出】
- **任务进度监控**：查看正在执行中的配送任务及其配送进度状态。【用户明确提出】
- **异常告警**：当出现配送机离线、路径冲突无法解决等异常情况时，监控界面显示告警信息。【推荐基线——用户明确要求"运行监控"，异常告警是监控的基本必要能力，否则异常无法被察觉】

## 5. 验收场景

### AC-01：配送任务可创建并入队等待分配

- 验收条件：创建配送任务后，任务进入等待队列并处于待分配状态，可在队列中查看到该任务。
- 入口类型：API
- 验证动作：创建一个包含目标桌位标识的配送任务。
- 预期结果：任务出现在队列中，状态为待分配，排队顺序符合创建顺序。
- 证据类型：other
- 证据说明：API 响应返回任务标识与待分配状态；队列查询接口可读回该任务。

### AC-02：空闲配送机可被分配队列任务并开始配送

- 验收条件：当有空闲配送机且队列中有待分配任务时，系统自动将任务分配给配送机，任务状态转为配送中。
- 入口类型：后台任务
- 验证动作：队列中有待分配任务时，将一台配送机置为空闲状态。
- 预期结果：系统将该任务分配给该配送机，任务状态从待分配变为配送中，配送机状态变为配送中。
- 证据类型：other
- 证据说明：任务状态查询返回配送中；配送机状态查询返回配送中。

### AC-03：多台配送机同时运行时路径不冲突

- 验收条件：两台或以上配送机同时执行配送任务时，系统协调路径，配送机不会在同一时段占用同一路径段。
- 入口类型：内部
- 验证动作：同时为两台空闲配送机分配不同桌位的配送任务，使两台配送机同时处于配送中状态。
- 预期结果：系统检测到路径冲突并执行协调，两台配送机的实际行进路径不发生冲突。
- 证据类型：other
- 证据说明：配送机路径记录显示无同时段同路径段占用；系统协调日志或状态可查。

### AC-04：配送机到达目标桌位时发送到桌通知

- 验收条件：配送机到达目标桌位时，系统发出到桌通知，通知包含目标桌位标识。
- 入口类型：API
- 验证动作：配送机执行配送任务并到达目标桌位。
- 预期结果：系统发出到桌通知，通知中包含目标桌位标识，接收方可据此确认配送已到达对应桌位。
- 证据类型：other
- 证据说明：通知记录可查，包含桌位标识与送达时间。

### AC-05：可取消队列中或配送中的任务并释放资源

- 验收条件：操作人员可取消待分配或配送中状态的任务，取消后任务状态变为已取消，相关资源被释放。
- 入口类型：用户界面
- 验证动作：分别对一个待分配任务和一个配送中任务执行取消操作。
- 预期结果：
  - 待分配任务：任务从队列移除，状态变为已取消。
  - 配送中任务：配送机停止配送并恢复空闲，路径资源释放，任务状态变为已取消。
- 证据类型：interaction

### AC-06：可监控队列状态、配送机状态和任务进度

- 验收条件：操作人员可在监控界面查看当前队列状态、配送机状态和正在执行的配送任务进度。
- 入口类型：用户界面
- 验证动作：进入运行监控界面，在系统中存在待分配任务和配送中任务的情况下查看监控信息。
- 预期结果：
  - 显示队列中待执行任务数量及各任务详情（目标桌位、状态）。
  - 显示每台配送机当前状态（空闲 / 配送中 / 离线）。
  - 显示配送中任务的执行进度状态。
- 证据类型：runtime-render

### AC-07：配送机离线等异常情况在监控界面显示告警

- 验收条件：当配送机离线或路径冲突无法解决等异常情况发生时，监控界面显示告警信息。
- 入口类型：用户界面
- 验证动作：使一台配送机进入离线状态，查看运行监控界面。
- 预期结果：监控界面显示该配送机的离线告警信息。
- 证据类型：runtime-render

## 6. 未规定事项

以下事项用户未明确规定，当前需求不做出假设或决定：

- 配送机的具体型号、数量上限和技术规格。
- 餐厅物理布局、桌位数量、路径地图的具体形式。
- 到桌通知的具体传递方式（如机器人自带屏幕、顾客手机推送、桌面终端等）。
- 运行监控界面的具体载体（Web、桌面端、移动端）和页面布局。
- 任务优先级机制（当前默认 FIFO，用户未要求优先级或插队规则）。
- 配送内容的具体形式（菜品、餐具、饮料等），需求仅要求任务携带目标桌位标识。
- 权限角色定义（如调度员、管理员、顾客的区分），用户未指定角色权限体系。
- 系统部署方式和技术架构选型。
