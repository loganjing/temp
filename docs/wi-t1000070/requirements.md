# 215-医院药品配送 需求说明

## 1. 目标

为医院药品院内配送建立一套可操作的配送管理能力，覆盖从配送订单接收、取药、送达、签收到异常处理的全过程，使每一次配送都有明确的责任人、可核验的身份以及可查询的状态记录。（用户明确提出：配送订单接收、取送点管理、身份核验、配送状态跟踪和异常处理五项能力。）

## 2. 参与方与职责

参与方为用户目标在实现上不可省略的最小集合，均为**推荐基线**，用户可调整：

| 参与方 | 职责 |
| --- | --- |
| 药房人员 | 提交/确认待配送药品订单，在取药点交付药品 |
| 配送员 | 接收配送订单，在取药与送达环节完成身份核验，推进配送状态，登记异常 |
| 收货人（病区护士站/科室/患者） | 在送达点完成身份核验并签收 |
| 配送管理员 | 维护取送点信息，查看全部配送单状态，处理配送异常 |

权限划分、角色是否合并、是否需要审批链属于**未规定**事项，本基线不预设权限模型。

## 3. 主流程

1. 药房人员在系统中登记一笔配送订单，选择取药点与送达点，填写药品明细与收货信息，订单进入「待取药」。（推荐基线）
2. 配送员接收该订单（可自行接单或由管理员指派，指派方式见 §6），在取药点核对取药信息并完成取药身份核验，通过后订单进入「配送中」。
3. 配送员到达送达点，与收货人核对身份并完成签收核验，通过后订单进入「已完成」，记录签收人与签收时间。
4. 任一环节出现缺药、破损、温控失效、送达点无人接收、地址或科室信息错误等情况时，配送员登记异常，订单进入「异常待处理」；管理员给出处理结论后，订单恢复流转或终止。

同一流程在第 4 节模块规则中不再重复展开，仅补充模块特定的行为与边界。

## 4. 功能需求

### 4.1 配送订单接收

- 支持通过界面接收一批待配送订单：登记医院/科室、取药点、送达点、收货人姓名与联系方式、药品明细（名称、规格、数量）、特殊要求（如冷藏、避光）、期望送达时间。（推荐基线；上游药房或医院信息系统的对接方式**未规定**，本基线以界面登记/接收作为验收入口，见 §6）
- 接收后的订单必须进入配送任务列表，可被配送员看到并推进，不允许出现"已登记但不可用于配送"的孤立订单。
- 订单在「待取药」阶段允许修改收货信息与药品明细；进入「配送中」后，药品明细不可再修改（避免与已交付实物不一致），收货信息变更需以异常或备注方式留痕。（推荐基线）
- 已完成的订单不可被再次取药或再次签收。

### 4.2 取送点管理

- 支持新增、编辑、启用/停用取送点；取送点包含名称、类型（取药点/送达点）、所属院区或楼栋、详细位置说明、联系人。
- 停用后的取送点不可被新订单选用，但已引用该点的历史订单仍可正常查看与推进，不因停用而阻断在途配送。
- 配送订单必须同时具备有效的取药点与送达点才能进入「待取药」；缺少任一取送点的订单必须先补齐。

### 4.3 身份核验

- 取药核验：配送员在取药点核对取药凭证（配送单号/取药码）与本人身份信息，核验通过方可取药并把订单推进为「配送中」；核验不通过时不得推进状态，允许重试并需登记原因。
- 签收核验：送达时核对收货人身份（姓名及联系方式或收货凭证），核验通过后完成签收，记录签收人、签收时间；核验不通过时不得完成签收，需转入异常处理（见 4.5）。
- 两次核验均需留痕：核验对象、核验方式、核验结果、核验时间、操作人，可在配送单详情中查看。
- 核验方式不限于某一种技术手段（人工核对、扫码、验证码等均可满足要求），实现方式属于**未规定**事项。

### 4.4 配送状态跟踪

- 配送单在列表与详情中展示当前状态、当前责任人、各状态的发生时间与操作人。
- 支持按状态、取送点、时间范围、配送员筛选查询配送单；支持查看单个配送单的完整流转记录。
- 状态变化必须以实际业务动作触发，不允许手工直接改写状态以跳过取药或签收核验。

### 4.5 异常处理

- 支持配送员在配送过程中登记异常，异常需包含类型（缺药/破损/数量不符/温控失效/送达点无人接收/信息错误/其他）、描述、发生环节、发生时间、登记人；必要时可附说明性文字。
- 登记异常后订单进入「异常待处理」，此时不可继续推进为已签收，也不计入正常完成。
- 管理员对异常给出处理结论：重新配送、退回药房、取消配送。处理后订单按结论恢复流转或终止，处理人、处理时间、处理结论与说明全程留痕，原始异常记录不可被删除或覆盖。

## 5. 可观察的业务状态

| 状态 | 进入条件 | 可执行动作 |
| --- | --- | --- |
| 待接单 | 订单已接收但尚未被配送员接收（推荐基线，可与「待取药」合并） | 接收、指派、修改订单信息 |
| 待取药 | 已具备有效取送点且被配送员接收 | 取药核验、登记异常、修改订单信息 |
| 配送中 | 取药身份核验通过 | 签收核验、登记异常 |
| 已完成 | 签收身份核验通过 | 查看、留痕查询 |
| 异常待处理 | 任一环节登记异常 | 补充说明、由管理员处理 |
| 已取消 / 已退回 | 异常处理结论为取消或退回 | 查看 |

## 6. 推荐基线与待确认事项

以下为闭合核心目标所需的最小推荐基线，均可调整：

1. **接单方式**：配送员自行接单 + 管理员可指派，两者同时存在。若只保留一种，验收动作相应简化。
2. **订单来源**：先以界面登记/接收为准，暂不对接院内药房系统或 HIS；对接上线后可替换入口，验收结果不变。
3. **状态粒度**：「待接单」与「待取药」可合并为「待取药」而不影响其余验收。

明确**未规定**、本基线不视为要求的内容：权限与角色合并方案、冷链温控数据采集、GPS/轨迹与路线优化、配送计费与结算、面向患者的通知推送、配送考核指标。

## 7. 验收场景

### AC-01：配送订单被接收并形成可配送任务
- 验收条件：登记一笔包含医院/科室、取药点、送达点、收货人、药品明细的配送订单后，系统生成配送单并进入可配送列表，初始状态为「待接单」或「待取药」；缺少取药点或送达点时不允许生成。
- 入口类型：用户界面
- 验证动作：在配送订单接收页面登记一笔完整订单并保存，再登记一笔未选择送达点的订单。
- 预期结果：完整订单出现在配送单列表中且状态为待接单/待取药，详情可看到全部填写内容；未选择送达点的订单被拒绝并给出明确提示。
- 证据类型：runtime-render, interaction, error-feedback
- 共享流程组：主配送流程

### AC-02：取送点可维护且与配送单正确联动
- 验收条件：取送点可新增、编辑、启停用；停用后的取送点不能被新订单选用；已引用停用取送点的在途订单仍可查看并继续推进。
- 入口类型：用户界面
- 验证动作：新增一个送达点，编辑其位置说明并停用；随后尝试新建引用该点的订单，并打开一张此前已引用该点的在途订单。
- 预期结果：新增与编辑结果可读回；新建订单无法选择已停用取送点；在途订单详情仍显示该取送点信息且状态可继续推进。
- 证据类型：runtime-render, interaction, session-persistence
- 共享流程组：取送点维护

### AC-03：取药环节必须通过身份核验才能推进配送
- 验收条件：未通过取药身份核验时订单保持「待取药」且不产生配送中的流转记录；核验通过后订单进入「配送中」，并记录核验对象、方式、结果、时间与操作人。
- 入口类型：用户界面
- 验证动作：对一张待取药配送单先提交错误取药凭证，再用正确凭证完成核验。
- 预期结果：第一次核验被拒绝，订单状态不变并提示核验失败；第二次核验成功后状态变为「配送中」，详情中出现包含操作人与时间的核验记录。
- 证据类型：interaction, runtime-render, error-feedback
- 共享流程组：主配送流程

### AC-04：签收环节必须通过收货人身份核验
- 验收条件：核验不通过时订单不得完成签收；核验通过后订单进入「已完成」并记录签收人与签收时间，已完成订单不可再次取药或再次签收。
- 入口类型：用户界面
- 验证动作：对一张配送中的订单先以错误收货人信息提交签收，再以正确信息完成签收，随后尝试对同一订单再次签收。
- 预期结果：首次签收被拒绝并提示核验不通过；正确签收后状态为「已完成」且显示签收人与签收时间；再次签收被阻止并给出提示。
- 证据类型：interaction, runtime-render, error-feedback
- 共享流程组：主配送流程

### AC-05：配送状态可跟踪、可筛选、可追溯
- 验收条件：配送单列表展示当前状态与责任人，支持按状态筛选；详情展示完整流转记录（状态、时间、操作人），记录与列表状态一致。
- 入口类型：用户界面
- 验证动作：在已完成若干状态变化的配送单上，按「配送中」筛选列表，并打开一条已签收订单查看流转记录。
- 预期结果：筛选结果只包含当前处于配送中的订单；已完成订单详情中的流转记录按时间顺序完整呈现且与列表状态一致。
- 证据类型：runtime-render, interaction, session-persistence
- 共享流程组：状态跟踪

### AC-06：配送异常可登记并使订单进入异常待处理
- 验收条件：登记异常后订单状态变为「异常待处理」，异常信息（类型、描述、发生环节、时间、登记人）可查询；处于异常状态的订单不能被签收完成。
- 入口类型：用户界面
- 验证动作：对一张配送中的订单登记「送达点无人接收」异常，随后尝试对该订单执行签收。
- 预期结果：订单状态变为「异常待处理」，详情可见完整异常信息；签收操作被阻止并提示需先处理异常。
- 证据类型：interaction, runtime-render, error-feedback
- 共享流程组：异常处理

### AC-07：异常处理结论驱动订单恢复或终止并全程留痕
- 验收条件：管理员给出处理结论（重新配送/退回药房/取消配送）后，订单按结论恢复流转或终止；处理人、处理时间、结论与说明可查，原始异常记录仍保留。
- 入口类型：用户界面
- 验证动作：对一条「异常待处理」订单分别以「重新配送」和「取消配送」两种结论处理（可用两张异常订单）。
- 预期结果：重新配送后订单回到可继续配送的状态并保留原异常与处理记录；取消配送后订单状态为已取消且不再可推进；两种情况下原始异常记录均未被覆盖或删除。
- 证据类型：interaction, runtime-render, session-persistence
- 共享流程组：异常处理

### AC-08：一次配送可从接收贯通到签收完成
- 验收条件：同一张配送单在连续流程中完成接收、取药核验、送达签收，最终状态为「已完成」，各环节经手人、时间与核验结果可回读且前后一致，无手工跳步。
- 入口类型：用户界面
- 验证动作：新建一张配送订单，依次完成接单、取药核验、签收核验，然后重新打开该订单详情与列表。
- 预期结果：订单详情呈现接收→待取药→配送中→已完成四段流转及对应操作人与时间，列表状态与详情一致，重新打开后数据仍在。
- 证据类型：interaction, runtime-render, session-persistence
- 共享流程组：主配送流程
