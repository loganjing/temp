# 工单系统需求（217-tickets）

## 1. 需求结论

**决策：ready。** 用户提出的工单管理、业务组分配、协作转派、处理与通知、满意度评价、统计分析、工作台与日志要求均可落成可观察的产品结果，无阻塞性澄清项。

说明：
- 用户明确提出的内容按原文落为基线与验收条件。
- 少量闭合缺口（角色承载、状态转换细则、统计口径）以**推荐基线**标注，保守、可逆、可观察，用户可直接调整。
- 用户未提出、也未由已确认基线隐含的内容（如 SLA 超时自动升级、多通知渠道）记为**未规定**，实现时不得自行补齐。

## 2. 目标与范围

建设一套面向多公司的工单系统：公司员工提交工单，公司内的业务组按分类承接与处理，全过程按公司隔离，并对工单量、响应效率、满意度与热点问题提供统计视角。

范围包含（用户明确提出）：工单台账与多轮回复、SLA 优先级与问题分类、按公司隔离、四段生命周期、业务组与成员、按分类自动分配、转派协作、提交人信息查看、处理人/处理时间记录与完成邮件通知、满意度评价、按公司与部门的统计、运营指标仪表盘、工单工作台、操作日志。

## 3. 角色与可见范围

| 角色 | 主要职责 | 来源 |
| --- | --- | --- |
| 提交人 | 提交工单、查看自己工单的进度与回复、对已完成工单评价 | 用户明确提出（提交人信息、用户评价） |
| 处理人 | 属于某公司业务组，承接/处理/转派/完成工单、回复工单 | 用户明确提出（业务组成员、转派、处理人记录） |
| 管理员 | 配置本公司的业务组、业务组成员、分类到业务组的自动分配规则 | 推荐基线 RB-1 |
| 平台运营 | 跨公司查看工单工作台与统计仪表盘 | 推荐基线 RB-2 |

可见范围（公司隔离规则）：

- 提交人只能看到自己提交的工单，不能看到同公司他人的工单。
- 处理人与管理员只能看到本公司的工单。
- 平台运营可跨公司查看与统计，并可按公司维度筛选（RB-2）。
- 任何角色都无法通过工作台、详情、回复、统计、日志入口获取非授权公司的工单内容。

## 4. 核心流程

1. 提交人创建工单：填写主题、描述、问题分类、SLA 优先级（P0–P4）；系统记录工单 ID、提交人信息（姓名、公司、部门、邮箱）与创建时间，工单归属提交人所在公司。
2. 分配：系统按本公司「分类 → 业务组」规则自动分配（命中则直接进入待处理）；未命中的进入待分配，由管理员或处理人指定业务组。
3. 处理：处理人打开工单，可同时查看提交人的姓名、公司、部门与该提交人的历史工单，进行多轮回复；需要其他业务组承接时执行转派。
4. 完成：处理人完成工单，系统记录处理人与完成时间，并向提交人邮箱发送完成通知。
5. 评价：提交人对已完成工单进行一次满意度评价。
6. 全流程的动作记录形成工单日志；工作台与统计仪表盘汇总展示运营情况。

| 信息项 | 说明 | 来源 |

| 主题 | 工单摘要标题 | 用户明确提出 |
| 描述 | 问题详情 | 用户明确提出 |
| 问题分类 | 标明工单所属问题类别，用于自动分配与热点统计 | 用户明确提出 |
| SLA 优先级 | P0、P1、P2、P3、P4 | 用户明确提出 |
| 提交人信息 | 姓名、公司、部门、邮箱 | 用户明确提出 |
| 创建时间 | 工单创建时刻 | 用户明确提出 |
| 所属公司 | 由提交人公司确定，作为隔离依据 | 用户明确提出（按公司隔离） |

| 处理人 / 完成时间 | 承接处理的人员与工单完成时刻 | 用户明确提出 |
| 满意度评价 | 已完成工单的评价结果 | 用户明确提出 |

## 6. 模块需求

### R-1 工单创建与台账
- 提交人可创建工单，必填主题、描述、问题分类、SLA 优先级；工单 ID、提交人信息、创建时间、所属公司由系统记录，不允许提交人手填。
- 创建成功后，工单出现在提交人自己的工单列表与管理侧工作台中，刷新或重新打开后仍可读取同一内容。

### R-2 多轮回复
- 提交人与处理人可在同一工单内多次回复，形成按时间顺序的对话记录。
- 每条回复记录回复人与回复时间，不做覆盖或替换；回复后工单详情刷新即呈现最新内容。

### R-3 公司隔离
- 工单归属提交人公司；所有读取入口（列表、详情、回复、统计、日志）均遵循第 3 节的可见范围。
- 越权访问不返回工单内容，并给出明确的拒绝反馈。

### R-4 SLA 优先级与问题分类
- 优先级取值为 P0–P4 五档，创建时设定，可被有权限的处理人在处理过程中调整（RB-3）。
- 问题分类来自系统维护的分类集合，可被自动分配规则与热点统计引用。

### R-5 生命周期
- 状态取值：创建、待分配、待处理、完成、取消。
- 转换规则（RB-4）：创建后立即进入待分配；命中自动分配规则时直接进入待处理；待分配与待处理可被取消；待处理可被完成；完成与取消为终态，进入终态后不可再变更状态、不可再回复、不可再转派。
- 每次状态变更记录变更前后状态、操作人与时间。

### R-6 业务组与成员
- 管理管理员可为所在公司新增多个业务组，并为每个业务组设置成员（RB-1）。
- 业务组归属于公司，不跨公司共享；同一人员可属于多个业务组。
- 移除成员后，该成员不再能看到该业务组承接的工单。

### R-7 按分类自动分配
- 管理员可为本公司配置「问题分类 → 业务组」的分配规则，同一分类在同一公司内至多命中一个业务组（RB-5，避免分配歧义）。
- 新建工单命中规则时自动分配到对应业务组并进入待处理；未命中则停留在待分配，并可由人工指定业务组。
- 人工指定与自动分配的结果都在工单上体现为「当前承接业务组」。

### R-8 转派
- 处理人可将工单转派给本公司其他业务组。
- 转派记录转派人、转派时间、原业务组与目标业务组；转派后工单仍为待处理，由目标业务组承接。
- 转派不改变工单的所属公司与提交人。

### R-9 处理与完成通知
- 处理人在工单详情中可查看提交人姓名、公司、部门与该提交人的历史工单（同公司范围内，含状态与主题等概览信息）。
- 处理人认领/首次处理时记录处理人（RB-6）；完成时记录完成时间。
- 工单完成时向提交人邮箱发送通知邮件；发送结果可被查看（成功或失败），失败时可重新发送（RB-7）。

### R-10 满意度评价
- 已完成的工单，提交人可提交一次满意度评价；评价维度与取值见 RB-8。
- 已完成但未评价的工单标记为「待评价」；重复提交不覆盖原有评价。
- 评价结果进入满意度统计。

### R-11 工单工作台
- 以列表形式展示工单，至少包含工单 ID、主题、分类、优先级、状态、所属公司与部门、提交人、处理人、创建时间。
- 支持按状态、优先级、分类、业务组、公司、部门筛选；支持按主题与工单 ID 搜索；支持按创建时间、优先级排序（RB-9）。
- 列表反映最新状态，操作后重新查询即呈现更新结果。

### R-12 统计与分析
- 按公司、部门维度统计工单分布（数量与占比），统计口径遵循当前角色的可见范围。
- 仪表盘展示工单量、平均响应时间、满意度、热点问题四类运营指标，并可选择统计时间范围（RB-10）。
- 指标定义遵循 RB-10，页面上的数值与同一范围内的工单明细可对得上。

### R-13 操作日志
- 记录工单相关操作：创建、状态变更、分配、转派、回复、完成、评价、邮件发送结果。
- 每条日志包含操作动作、操作人、操作时间与结果；同一工单的日志按时间顺序呈现。
- 日志不可被普通角色修改或删除。

## 7. 推荐基线与未规定事项

### 推荐基线（为闭合核心目标的最小假设，可调整）

- **RB-1 配置角色**：业务组、成员与分配规则的配置由「管理员」承担，管理员属于具体公司，只能配置本公司范围。
- **RB-2 跨公司视角**：因用户要求「按公司维度筛选」与「按公司、部门维度统计」，需存在可跨公司查看的角色，命名为「平台运营」；其只读查看与统计，不代为处理工单。
- **RB-3 优先级调整**：处理人可在待处理阶段调整优先级，调整记录进入日志。
- **RB-4 状态转换**：见 R-5 的转换细则；完成与取消为终态。
- **RB-5 分类规则唯一性**：同一公司内同一分类只对应一个业务组，避免自动分配歧义。
- **RB-6 处理人记录时机**：处理人认领或首次回复时记录；完成时保留该处理人并记录完成时间。
- **RB-7 邮件通知**：仅发送给提交人邮箱，内容包含工单 ID、主题与完成提示；系统保留每封通知的发送状态并支持失败重发，以保证通知结果可观察。
- **RB-8 评价方式**：单一整体满意度，1–5 分，可选填写意见文本；每张工单一次。
- **RB-9 工作台能力范围**：筛选、搜索、排序的字段以上述列举为限。
- **RB-10 统计口径**：
  - 平均响应时间 = 从工单创建到首次回复的平均时长（按筛选范围内已产生首次回复的工单计算）。
  - 满意度 = 评价分数的平均值，并同时展示评价数量。
  - 热点问题 = 按问题分类聚合的工单量排序结果，展示排名靠前的分类。
  - 时间范围默认最近 30 天，可切换。

### 未规定（不得自行补齐）

- SLA 时限数值、超时预警与按优先级自动升级机制（用户仅要求优先级设置）。
- 除邮件外的通知渠道（短信、站内信、即时通讯）。
- 移动端/桌面端等具体载体与设备适配形态（本需求只声明交互入口为用户界面）。
- 工单附件、知识库、满意度回访、外部系统集成。
- 提交人自助注册、公司/部门/人员档案的维护方式（视为已有基础数据）。

## 8. 验收场景

### AC-01：提交人可创建工单并读回
- 验收条件：提交人填写主题、描述、问题分类、SLA 优先级后创建工单，系统生成工单 ID，并记录提交人姓名、公司、部门、邮箱与创建时间；创建后可在自己的工单列表中读回该工单，内容一致。
- 入口类型：用户界面
- 验证动作：以提交人身份打开新建工单入口，填写必填项并提交，随后在提交人自己的工单列表中打开该工单。
- 预期结果：提交成功并显示工单 ID；列表中可找到该工单，详情中的主题、描述、分类、优先级、提交人信息、创建时间与提交内容一致。
- 证据类型：runtime-render, interaction, session-persistence

### AC-02：工单支持多轮回复并保留回复人与时间
- 验收条件：提交人与处理人可在同一工单内多次回复，每次回复记录回复人与回复时间，历史回复不被覆盖，双方均可在工单详情中看到完整对话。
- 入口类型：用户界面
- 验证动作：在已分配的工单中依次由处理人回复、提交人回复、处理人再次回复，然后分别以两种角色打开该工单详情。
- 预期结果：详情按时间顺序展示全部回复，每条带回复人与回复时间；再次进入该工单时内容不丢失。
- 证据类型：runtime-render, interaction, session-persistence

### AC-03：工单状态按生命周期流转且终态锁定
- 验收条件：工单状态取值为创建、待分配、待处理、完成、取消；状态按 R-5 的规则转换，完成与取消后不可再变更状态、不可再回复、不可再转派。
- 入口类型：用户界面
- 验证动作：新建一张未被自动分配规则命中的工单，观察其状态；为其指定业务组；由处理人完成该工单；对另一张工单执行取消；分别尝试对已完成与已取消工单回复。
- 预期结果：新工单为待分配，分配后变为待处理，完成后为完成，取消后为取消；对终态工单的回复入口不可用或操作被拒绝，且状态保持终态。
- 证据类型：runtime-render, interaction, error-feedback

### AC-04：SLA 优先级与问题分类可设置并在工单上呈现
- 验收条件：优先级取值为 P0–P4 五档，问题分类取系统维护的分类集合；两者在创建时设定，并在工单详情与工作台列表中正确呈现。
- 入口类型：用户界面
- 验证动作：分别以 P0 与 P4 创建工单指定不同问题分类，然后在工单详情与工作台列表中查看这两张工单。
- 预期结果：优先级与分类按提交值显示，取值不越出 P0–P4 与既有分类集合。
- 证据类型：runtime-render, interaction

### AC-05：工单按公司隔离
- 验收条件：不同公司的用户只能看到授权范围内的工单（见第 3 节），无法通过列表、详情、回复、统计或日志获取其他公司的工单内容。
- 入口类型：用户界面
- 验证动作：在 A、B 两家公司各创建工单，分别以 A 公司提交人、A 公司处理人、B 公司处理人身份访问工作台与直接打开对方工单详情。
- 预期结果：A 公司提交人只看到自己提交的工单；A、B 公司处理人只看到本公司工单；越权打开对方工单时被拒绝且不显示工单内容。
- 证据类型：runtime-render, authorization, error-feedback

### AC-06：可为公司配置多个业务组及成员
- 验收条件：管理员可为所在公司创建多个业务组，并为每个业务组添加、移除成员；业务组与成员不跨公司共享。
- 入口类型：用户界面
- 验证动作：以管理员身份在 A 公司创建两个业务组，分别为其添加成员，再移除其中一个成员；以被移除成员身份访问该业务组承接的工单。
- 预期结果：两个业务组及其成员关系正确保存并可再次读取；被移除成员不再能访问该业务组承接的工单；B 公司管理员看不到 A 公司的业务组。
- 证据类型：runtime-render, interaction, authorization, session-persistence

### AC-07：工单按分类自动分配到业务组
- 验收条件：管理员可为本公司配置「问题分类 → 业务组」规则；新建工单命中规则时自动分配到该业务组并进入待处理，未命中则停留待分配并支持人工指定业务组。
- 入口类型：用户界面
- 验证动作：为某分类配置业务组规则后，提交一张该分类的工单；再提交一张未配置规则的分类的工单；随后对后一张工单人工指定业务组。
- 预期结果：第一张工单承接业务组为规则中的业务组且状态为待处理；第二张为待分配、无承接业务组；人工指定后其承接业务组更新并进入待处理。
- 证据类型：runtime-render, interaction, session-persistence

### AC-08：工单可转派并留下转派记录
- 验收条件：处理人可将本公司工单转派给其他业务组，转派后工单仍为待处理并由目标业务组承接；工单所属公司与提交人不变，转派动作被记录。
- 入口类型：用户界面
- 验证动作：以处理人身份将一张待处理工单转派到本公司另一个业务组，然后查看工单的承接业务组与操作记录。
- 预期结果：承接业务组变为目标业务组，状态仍为待处理，所属公司与提交人不变，操作记录中出现转派人、转派时间与原/目标业务组。
- 证据类型：runtime-render, interaction, session-persistence

### AC-09：处理工单时可查看提交人完整信息与历史工单
- 验收条件：处理人在工单详情中可查看提交人的姓名、公司、部门与该提交人的历史工单（同公司范围内），不跳转其他系统即可完成了解上下文。
- 入口类型：用户界面
- 验证动作：让同一提交人提交多张工单，由处理人打开其中一张的详情并查看提交人信息区域。
- 预期结果：详情中显示提交人姓名、公司、部门与邮箱，并列出该提交人的历史工单概览；历史工单不含其他公司的内容。
- 证据类型：runtime-render, authorization

### AC-10：完成工单记录处理人与时间并发送邮件通知
- 验收条件：处理人完成工单时，系统记录处理人与完成时间，并向提交人邮箱发送完成通知；通知的发送结果可查看。
- 入口类型：用户界面
- 验证动作：以处理人身份完成一张工单，查看工单详情中的处理人、完成时间，并在通知记录中查看该工单的邮件发送结果。
- 预期结果：处理人为执行完成的处理人，完成时间与操作时刻一致；通知记录中存在面向提交人邮箱的完成通知及其发送状态。
- 证据类型：runtime-render, interaction, other

### AC-11：提交人对已完成工单进行满意度评价
- 验收条件：已完成工单可由提交人提交一次满意度评价；未评价的已完成工单标记为待评价；评价后按 RB-8 计分，重复评价不覆盖首次结果。
- 入口类型：用户界面
- 验证动作：以提交人身份对一张已完成工单提交满意度评价，再次尝试提交同一工单的评价，并检查未评价的另一张已完成工单。
- 预期结果：首次评价成功保存并显示；第二次提交被拒绝或不可编辑；未评价的已完成工单显示待评价状态。
- 证据类型：runtime-render, interaction, session-persistence, error-feedback

### AC-12：工单工作台支持筛选、搜索与排序
- 验收条件：工作台列表展示工单 ID、主题、分类、优先级、状态、公司、部门、提交人、处理人、创建时间，并支持按状态/优先级/分类/业务组/公司/部门筛选、按主题与工单 ID 搜索、按创建时间与优先级排序。
- 入口类型：用户界面
- 验证动作：在工作台中依次按公司筛选、按状态筛选、按工单 ID 搜索、按创建时间倒序排序，并查看结果条数。
- 预期结果：每次操作后列表仅包含符合条件且在权限范围内的工单，条数与实际匹配数量一致；排序结果顺序符合所选字段。
- 证据类型：runtime-render, interaction, authorization

### AC-13：按公司与部门维度统计工单分布
- 验收条件：统计视图可按公司、部门维度展示工单数量与占比，数值与同样条件下的工单明细一致，且遵循当前角色的可见范围。
- 入口类型：用户界面
- 验证动作：以平台运营身份打开统计视图，查看按公司维度的分布与按部门的分布，并与工作台按同样条件筛选后的条数比对。
- 预期结果：分布数值与工作台筛选结果一致，各维度合计与该范围内工单总数一致。
- 证据类型：runtime-render, interaction, authorization

### AC-14：运营仪表盘展示核心指标
- 验收条件：仪表盘展示工单量、平均响应时间、满意度、热点问题四类指标，并支持选择统计时间范围；指标口径遵循 RB-10。
- 入口类型：用户界面
- 验证动作：在仪表盘选择统计时间范围，记录四类指标数值；在同一范围下于工作台核对工单数量与已评价工单的评分，核对按分类聚合的工单量。
- 预期结果：工单量与该范围内工单数一致；平均响应时间对应创建至首次回复的平均时长；满意度值与评价数量与明细一致；热点问题按分类工单量排序且与明细吻合。
- 证据类型：runtime-render, interaction

### AC-15：工单相关操作形成可追溯日志
- 验收条件：创建、状态变更、分配、转派、回复、完成、评价与邮件发送结果均产生日志，日志包含操作动作、操作人、操作时间与结果，并按时间顺序呈现；普通角色不能修改或删除日志。
- 入口类型：用户界面
- 验证动作：对一张工单依次执行创建、自动分配、回复、转派、完成、评价，然后打开该工单的日志。
- 预期结果：日志按时间顺序覆盖上述动作及其操作人与时间，条目与该工单的实际操作一致；界面不提供修改或删除日志的入口。
- 证据类型：runtime-render, interaction, session-persistence
