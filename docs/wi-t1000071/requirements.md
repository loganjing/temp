# 教师管理系统 需求基线

## 目标

提供一个教师信息管理系统，支持对教师记录进行新增、查看、编辑、删除。教师记录固定包含五个信息项：教师名称、教授课程、年级、手机、邮箱。数据通过平台提供的 dbkit 数据库存储（用户明确提出），因此新增或修改后的记录在页面刷新后仍应可读回。

## 范围与来源

- 用户明确提出：教师增删改查；字段为教师名称、教授课程、年级、手机、邮箱；使用 dbkit 的数据库存储。
- 推荐基线（保守、可调整，非用户原话）：
  - 教师名称为必填项；手机、邮箱在填写时做基础格式校验（手机为 11 位数字，邮箱含 "@" 与域名部分），不通过时给出可读的提示且不保存该记录。
  - 允许存在同名教师，教师名称不作为唯一标识；记录以系统内部标识区分。
- 未规定（本次不据此验收，如需要可另行补充）：登录与角色权限、分页/搜索/排序、课程与年级的下拉候选项与字典维护、批量导入导出、删除留痕与恢复、多端实时同步。
- 本次不决定数据库表结构、接口形态与前端技术方案；这些属于后续设计阶段。

## 核心行为与规则

1. 记录字段：教师名称（文本）、教授课程（文本）、年级（文本或年级值）、手机（文本）、邮箱（文本）。五个字段均随记录一起展示与编辑。
2. 新增：填写五个字段并保存成功后，该教师出现在教师列表中，展示值与填写值一致；刷新页面后仍可读回。
3. 查看：教师列表展示全部已保存教师及其五个字段值；可查看单条教师的完整信息。
4. 编辑：修改已有教师的一个或多个字段并保存成功后，列表与详情展示为修改后的值；刷新页面后仍为修改后的值。
5. 删除：删除某条教师记录后，该教师不再出现在列表中；刷新页面后仍不出现。
6. 校验：必填缺失或手机、邮箱格式不符合推荐基线时，保存被拒绝并提示具体原因，列表中不产生或不变更为无效数据。

## 验收场景

### AC-01：新增教师后可在列表读回
- 验收条件：填写教师名称、教授课程、年级、手机、邮箱并保存成功后，教师列表出现该教师，五个字段值与填写值一致；刷新页面后该记录仍存在且值不变。
- 入口类型：用户界面
- 验证动作：在教师管理界面新增一条包含五个字段的教师记录并保存，随后查看列表并刷新页面。
- 预期结果：列表中可看到该教师及五个字段的正确取值，刷新后结果一致。
- 证据类型：runtime-render, interaction, session-persistence

### AC-02：必填与格式校验阻止无效保存
- 验收条件：教师名称为空，或手机、邮箱格式不符合基础格式规则时，保存被拒绝，界面提示对应的具体原因，列表数据不被新增或改写。
- 入口类型：用户界面
- 验证动作：分别提交缺少教师名称的记录和手机或邮箱格式错误的记录并保存。
- 预期结果：保存未生效，界面显示与所违反规则对应的提示，列表保持原有数据。
- 证据类型：interaction, error-feedback

### AC-03：编辑教师信息并读回更新结果
- 验收条件：修改已有教师的一个或多个字段并保存成功后，列表与详情展示修改后的值；刷新页面后仍为修改后的值。
- 入口类型：用户界面
- 验证动作：选择一条已保存的教师，修改其教授课程与手机并保存，随后查看列表与详情并刷新页面。
- 预期结果：展示值为修改后的值，刷新后保持一致，其他未修改字段不变。
- 证据类型：runtime-render, interaction, session-persistence

### AC-04：删除教师后从系统移除
- 验收条件：删除某条教师记录后，该教师不再出现在教师列表中；刷新页面后仍不出现，其他教师记录不受影响。
- 入口类型：用户界面
- 验证动作：对一条已保存的教师执行删除，随后查看列表并刷新页面。
- 预期结果：该教师从列表中消失，刷新后仍不出现，其余记录保持可见。
- 证据类型：interaction, session-persistence
